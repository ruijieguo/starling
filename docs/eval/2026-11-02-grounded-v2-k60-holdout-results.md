## 2. 设计

- **留出集**：LongMemEval-S 500 题里排除所有用过的题（tau 标定、H2 确认、11-01 评测，共 452 题）后剩下的 **48 题，全部是 multi-session**：44 题可答，4 题弃答。冻结前没有看过任何题面。
- **2×2**：A = v1 + k30（现行）、B = v2 + k30、C = v1 + k60、D = v2 + k60。A/B 共用同一份上下文，C/D 共用同一份；逐题核对一致性，192 条全部通过。
- **模型**：抽取与作答用 zengen-27B（本地 vLLM，关推理）；判分用 deepseek-v4-pro，官方 multi-session yes/no 模板，每题判两次取均值。
- **判据**：配对差的 bootstrap 95% 下界 > 0，弃答错误不超过 A + 1，无回复不超过 2/44。两项分开判定。
- **检验力**：冻结前就已写明，44 题只能检出约 +0.11 以上的效应。

## 5. 判分网关故障与修订

预注册冻结后、结果出来之后，发现约 10% 的判分调用根本没有到达判分模型：提示 token 为 0，返回 `permanent_400`。`judge.py` 把这些调用记成了 0 分。

- **原因**：tokenkey 网关对少数特定提示内容稳定返回 400（报“AgentPlan subscription”），原因不明，同一提示走 galaxywave 网关能成功。两个网关返回的模型都是 `deepseek-v4-pro-ga-260813`。11-01 的三套判分里这类失败为 0，所以 #117 和 #118 的报告不受影响。
- **处理**（预注册修订 1）：失败的调用不再计 0 分，最多重试 6 次；仍失败的行改走 galaxywave 重判。规则只看调用是否到达了模型，四臂同样处理；每条判分都标明网关。
- **A/A 校验**：LME 120 的 A 臂与 11-01 配置相同，上下文和提示逐字节一致。修订前比 11-01 低 0.089 [−0.147, −0.031]，修订后差 +0.009 [−0.018, +0.036]，只有 3 题翻转。由此确认修订后的判分可信。
- **修订前的数字**（留出集 A/B/C/D 为 0.614 / 0.648 / 0.670 / 0.705，叠加为 +0.091）曾向用户汇报过，现已作废。当时说的“方向一致、赢多输少”是失败调用计 0 造成的假象。

**教训**：判分脚本必须区分“模型判了 no”和“调用失败”。`judge_yes_no` 已改为失败时重试，仍失败则标记 `judge_failed`，不计分。

留出集的题型（multi-session 计数、汇总）恰好不是 v2 和 k60 主要起作用的地方：v2 主要帮时间题，k60 主要帮单跳和多跳召回。所以这次验收**没能检验两项改进最可能起作用的场景**。

## 7. 读这些数字要注意的地方

- **留出集只有 multi-session 一类。** LME 里时间推理和知识更新两类早已用完，结论不能外推到这两类，也不能外推到单会话和偏好类。
- **“不通过”不代表“无效”**，只说明 44 题的量下没有可靠证据。不过修订后，能改变结论的题只有两三道，即使有效果也很小。
- **v2 的措辞是看过诊断集错例后写的**，所以诊断集（LME 120、LoCoMo）上的分数必然偏乐观。LoCoMo 上 v2 为 +0.026，但 LME 120 上只有 +0.000，两个诊断集的结果也不一致。
- k=60 让上下文约增加 37%–58%，作答成本和延迟随之上升，本次没有测延迟。

## 8. 下一步建议

- **按预注册，生产配置不变**：k_source 保持 30，作答指令保持 v1。
- 证据的分布：LoCoMo 上两项都为正，并且正好落在诊断时预期的类别上（v2 → 时间题，k60 → 多跳、开放域、单跳）；唯一的验收集只覆盖 multi-session，恰好不是这两项主要起作用的场景。
  所以“不通过”主要说明**验收集覆盖不到**，而不是改进被否定。
- 如果要让这两项上线，需要一个**覆盖时间题和单跳题的新留出集**。现有基准里：LME 的时间推理题已经用完；BEAM 全系列已经用完；LoCoMo 只有 10 段对话，已全部用作诊断。可选的路是新数据源，或者自建一小批题。
  这个选择要由用户来定。
- 不建议做的：依据 LoCoMo 的结果直接上线。这正是事先说好不该做的“在诊断集上验收”。
