# SocialMemBench R6.8：C++ 原生结构化来源选择评测报告

## 结论

R6.8 已完成中文设计、失败测试、C++ 实现、来源准备、133 次真实选择、同期 QA 和独立核验。固定 133 题开发集上，v9 正确 52/133（39.10%），selector 正确 60/133（45.11%），净变化 +6.02 个百分点；六网络聚类 bootstrap 95% 区间为 [-5.60, 16.28] 个百分点。

预设扩展开发门槛未通过（候选正常率低于 v9，区间跨零）；因此不晋升默认策略，也不把这次增益宣称为生产收益。结果只覆盖同八库、六网络的 133 题开发集，不是完整 SocialMemBench 或保留集成绩。

## 清理边界与实验实现

本轮开始前已删除 4,041 个未封存、可重建的 CMake 编译中间文件，目录占用减少 612.48 MiB；175,908 个保留文件和 207 个身份/封存清单逐项核验一致。数据库、模型回答、HTTP/费用回执、诊断文档、动态核心和测试可执行文件均保留，清理没有产生模型请求，也没有停止其他进程。详见 [清理报告](2026-09-26-evaluation-artifact-cleanup.md)。

R6.8 新增 C++ `SourceSelectionV1/JsonObject` 入口：C++ 收集完整授权来源池，模型只提议来源编号，C++ 负责编号、归属、数量和 UTF-8 预算验证并渲染原始来源。池上限为 1,000 行/131,072 字节，输出上限为 20 条/8,000 字节；Python 只负责 binding、冻结、编排、审计和统计。新核心 SHA-256 为 `f851c2f3a5bd23590c6f51aba34426e6aba7872737ac54e7f745cc3d593bea29`。回答和 HTTP 审计继续使用独立的 R6.2 核心，不把结构化选择能力冒充为全链路生产验证。

两臂回答均使用 qwen3.8-27b、grounded_memory_v1、1024 输出预算和关闭 thinking；裁判为 64 预算、120 秒超时、零重试、并发 4。selector 额外承担每题一次、512 预算的完整池选择调用，因此两臂总推理成本不相等。

## 结构化输出合同诊断

133/133 次选择回执都带有 `source_selection_v1` 和 `json_object` 合同；localhost binding/HTTP 测试已断言实际请求体包含 `response_format.type=json_object`。R6.7 的 Markdown 围栏失败由 3 题降为 0 题。R6.8 仍有 3 题因模型提出超过 20 个编号而被 C++ 拒绝，未截断、未补选、未回退，原始回执保留并计入完整分母。

## 健康、成本与并发事件

选择阶段实际 133 次 HTTP，已知/总 tokens 为 2,552,139，usage 完整；QA 阶段实际 473 次 HTTP，已知 tokens 1,155,546，6 次缺 usage，总 tokens 保持未知（null）。两阶段合计 606 次 HTTP，已知 tokens 3,707,685；缺失 usage 没有按零消费处理。

QA 启动时曾有一次并发创建 `qa-prepare` 目录的竞态：第二个进程在进入请求阶段前因目标目录已存在退出；另一进程完成了 266 个唯一终态和 266 条 settled 账本。该事件只影响启动编排，没有产生重复回答/裁判请求，也没有改变正式 133 题分母；`qa-chain.log` 的 traceback 和最终封存账本均保留作为审计证据。

## 下一轮优化顺序

1. 在 C++ 中增加可执行预算计划：先要求模型返回候选优先级、必要事件角色和阶段覆盖，再由原生执行器在 20 条/8,000 字节内稳定分配；超限继续显式失败并记录原因。
2. 针对 Q6 类群体规范题增加成员覆盖、反例和例外的离线反例；针对 Q8 类变化题增加前态—触发—后态三段覆盖，先用冻结来源池消融验证上下文是否真正改善。
3. 把来源选择、回答、裁判的健康率和完整成本分开设门；修复并发启动幂等后，再做同口径真实复评。达到门槛后才扩大到未参与开发的题目/网络。

## 收尾架构复审修复（2026-09-27）

代码审查发现归因阶梯 S_star 的 Python 分支重复执行 holder 枚举、逐 holder planner 调用和候选融合。
该路径已改为调用 C++ `observer_holders` 与 `ObserverRetriever(mode=statements)`；候选排序、去重、预算和
渲染均由原生核心完成。Python 只保留评测编排与结果解析，并新增守门测试防止检索逻辑回流到 binding。

同时，评测编排层规范化查询时间，`ObserverRetriever` 在 C++ 中校验并回传 `as_of_iso`，修复 real-mode 诊断无法核对查询时点的问题。
收尾构建的 C++ 全量回归为 1395 项：1372 项通过、23 项跳过、0 项失败。R6.8 历史封存结果仍保持
原始程序哈希；由于本次收尾改变了 `eval_ladder_pipeline.py`，历史封存校验对当前工作树报告 Python
源码漂移，这是封存边界的预期阻断，不重新生成或改写历史评测结果。

