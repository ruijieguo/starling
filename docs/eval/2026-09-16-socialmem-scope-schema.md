## 真实结果与原因

| 项目 | C0 旧 schema | C1 新 schema |
|---|---:|---:|
| 实际 HTTP 请求 | 8 | 8 |
| HTTP 200 | 8 | 6 |
| HTTP 400 | 0 | 2 |

C1 的 JSON object 探测与严格准入探测通过。JSON object 模式没有向提供商发送此严格数组 schema，不能用其通过推断关键字受支持。严格抽取两次均返回同类错误：

```text
Format error : 'response_format.json_schema.schema'.
When the schema contains the fields "uniqueItems", "contains", "minContains", or "maxContains",
the type should not be "array".
```

这是请求 schema 兼容性失败，没有对应的模型抽取结果。原生能力状态保留 `unknown:permanent_400`；分析层记录提供商返回的 schema 参数拒绝，不能把它记为模型语义错误。新 schema 同时包含两个关键字，因此 `minItems` 单独是否可用仍未知。

官方结构化输出页面未提供这两个关键字的明确逐项支持列表；文档查询过程、快照和错误均已保存。实际响应是当前 endpoint/model/schema 组合的兼容性证据，不外推到其他服务或模型。

14 个成功响应报告的已知 token 合计 34257（C0 22280，C1 11977）；两次 HTTP 400 未提供 usage，不能据此推断计费为零。预算 reservation 与独立核算的实际 HTTP 次数均为 16。

## 后续优化方案

建议下一轮在 C++ 分离“完整本地契约”与“提供商请求 schema”：本地仍严格检查非空、去重、主范围及来源语义；为该提供商配置显式、版本化的 wire schema，避免发送已被拒绝的 `uniqueItems`。该方案不允许在一次失败请求中自动删字段、换模式或重试。

先文档明确两种 schema 的职责和各自哈希，再写测试确保 wire 省略不支持关键字时，本地重复标记仍被拒绝、合法复合标记保留、能力报告绑定正确 profile。最后实现 C++，用新的小额探测验证 `minItems` 单独兼容性；通过后再单独冻结来源覆盖实验。候选覆盖验证通过后才考虑入库、检索、QA 和裁判。此后续方案尚未实施，也没有追加真实调用。
