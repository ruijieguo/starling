# SocialMemBench 保留种子的连续对话扩展设计

本设计先于测试和实现写入，按用户持续自主迭代及DashScope授权执行。核心逻辑C++，Python只绑定、透传配置、编排和统计。既有main工作区继续使用，不提交或清理既有修改；独立build实验目录保存每轮身份。上一轮3924封存文件已逐项核验，345份旧文档与6份待修改代码已快照到build/socialmem_dialogue_checks/。

## 诊断、选择和限制

两阶段证据回答313/733，低于同容量grounded父345/733，且tokens增加69.46%；引用匹配不验证模型解释。原focused_window每六次选择只预留一次邻接机会，种子可能包含关键发言却遗漏对话双方的确认或反驳。下一轮要验证可复用的连续话轮扩展能力，不新增模型解释。

比较三条路径：仅扩大focused_window的k/字节预算会改变种子集合，无法保证保留已有证据；删除规划解释可作后续消融，但不补齐漏召的回应；本轮选择保留旧检索种子、增加已授权连续邻接。它同时改变组织策略和容量，不能称等上下文预算或把增益全部归因于邻接。不是语义事件识别或因果推断实现。

## 原生契约

ObserverQuery新增source_seed_k（默认10）、source_seed_max_context_bytes（默认4000）、source_dialogue_radius（默认2）。新增source_strategy="focused_dialogue"，只适用于sources。其他策略忽略新字段，原block、refs、诊断必须兼容。新策略要求0<seed_k<=k，0<=seed_bytes<=max_context_bytes，0<=radius<=8；边界不合法在查询前抛出invalid_argument。

算法仅接收已经通过tenant、allowed_holders、登记时间、观测时间、擦除、保留策略、哈希与去重过滤的来源：

1. 按当前BM25顺序保留完整候选池，用旧focused_window及seed_k/seed_bytes选种子。无显式人物时使用旧BM25回退。无论旧路径是否激活人物路由，都按旧渲染的整行预算和k准确取种子；种子文字和完整引用不得改变或丢失。
2. 为非空session和有效数值turn_index建立位置索引。扩展只从种子出发，按距离1→radius，每层以种子在原BM25候选池的优先级、前一轮→后一轮访问。相同位置有多个已授权来源时按原BM25稳定顺序处理，去重；不把邻接当成已验证回复或因果边。
3. 每个方向必须存在已授权的连续中间位置；某位置缺失或被过滤，不跳过空缺继续向更远处扩展。跨session、缺失/空session、未知turn_index不得扩展；整数边界不能溢出。只要求位置存在，不要求每个中间话轮都因预算而被选入。
4. 先保留全部种子，再在总k和UTF-8字节预算内加入完整话轮。装不下的来源跳过，不截断文本，不为补邻接驱逐种子；剩余预算不以无关全局发言填满。最终按旧时间/session/turn_index/稳定身份排序，block和source_refs同序。
5. source_diagnostics记录新策略、seed_count、added_sources、radius和种子预算；既有filtered等诊断保留。半径0精确保留种子集合和文字；无可见种子不扩展。

实现位于source_retriever.hpp/.cpp，binding只暴露字段。eval_ladder_pipeline和run_socialmem_baseline仅在配置中存在时透传三字段，不复制选择、邻接、排序或字节逻辑；避免影响加载旧冻结核心的旧调用。
