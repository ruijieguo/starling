# SocialMemBench 人物与会话覆盖检索设计

状态：C++实现、真实对照及独立统计核账已完成；封存与最终复验以机器回执为准。用户已授权自主迭代；保持当前工作区，不提交或切换分支。遵循中文文档→失败测试→C++实现→冻结评测→分析与设计同步。

## 已确认问题

上一轮99题四组合没有稳定收益。C++原生只读重放（数据库使用临时副本）进一步确认：膝盖原话在全部160条合格来源中排名159、本人11条中排名11；菜单早态在170条中排名112、本人28条中排名23。两者均不在focused_window的30条种子中，距它们两轮以内也无种子。只围绕种子扩展，无法触达这些第一人称、低词项匹配的事实。

证据：build/socialmem_coverage_checks/initial-native-diagnostic.json。已读取开发案例及参考答案，因此这些案例只用于诊断，不包装成独立验证集。候选不读取题号、参考答案或锚点。

## 方案与取舍

选择保留旧种子、增加人物/会话覆盖的有限改动。单纯扩大k会改变容量且继续受排名限制；直接改写BM25会影响全部种子。新方案保持旧种子，将扩展预算的一部分用于跳出种子邻域，同时可能牺牲邻句支持，需要同期对照检验。

新增显式`source_strategy=focused_coverage`，仍仅允许sources模式，复用现有seed_k、seed字节及radius字段，不增加Python选择规则。默认bm25及既有策略不变。

1. 完全复用现有租户、holder、时间、擦除、原文哈希、去重过滤，以及focused_window种子选择。种子在原始seed预算内先全部保留。
2. 仅对题目已匹配的显式人物建立补充队列。每人按非空session分组，缺失session单列一组，组内保持BM25排序；会话组按其最早合格发言的既有chronological顺序排列。按题干人物顺序轮转，每人再按会话轮转，跳过已选条目。
3. 覆盖阶段最多新增`floor((k-seed_count)/2)`条，字节上限为`seed_bytes + floor((max_context_bytes-seed_bytes)/2)`。超长整行跳过继续搜索，不能切分原文；一人的队列耗尽不阻塞其他人。没有可匹配人物来源时，block及refs精确回退focused_dialogue。
4. 覆盖后按既有算法围绕原种子扩展±radius连续授权话轮，使用剩余总预算。不把新增覆盖发言递归作为新种子，避免扩展范围失控。最终统一按原chronological顺序呈现。
5. 仅新策略返回`selection_trace`，逐条记录合格来源ref、BM25排名、是否原种子、是否覆盖候选、覆盖/邻接是否考虑及字节拒绝、最终selected_by。计数上限是否达到由阶段汇总记录，不给未遍历来源捏造唯一拒绝原因。trace不进入LLM提示，不含被权限/时间/完整性排除的来源。

覆盖只是证据选择，不推断事件时间、态度变化或因果，不自动纠正人物语义，也不代表结构化记忆闭环已实现。
