> **范围 Schema 对齐收口（2026-09-16）**：C++ 非空/去重约束与评测身份/预算守卫已实现；真实 16 次请求、零重试，C0 8/8，C1 因提供商拒绝数组 uniqueItems 为 6/8，按门槛停止。四来源覆盖及 QA 未执行，无新 F1。详见[本轮报告](../../eval/2026-09-16-socialmem-scope-schema.md)。


**状态（2026-09-16）：已实现状态覆盖指导、共享关系目录和裸短语守卫；模块身份已纠正并完成回归，真实评测已获授权。** 本设计承接 [声明范围定位与生成覆盖诊断](2026-09-15-claim-scope-localization-design.md) 及 [谓词覆盖与证据设计](2026-09-13-relation-evidence-coverage-design.md)。

## 1. 背景与目标

L/R0 已修复句首声明被后续问句误拒的问题，但固定 S/T 原文显示 Marcus 的三类可表达状态没有进入候选：未决选择、已经决定并搬迁、重新开始带来的紧张。此前的本地关系修复还发现认知内容误标 `feels`、`objecting` 缺少反对目标。

本阶段目标是提高可表达状态的生成覆盖，并减少关系、对象、时间信息丢失。目标是建立可审计的 C++ 提示与契约边界，不以增加候选数量作为成功标准，不修改冻结金标，不把人工解释写成直接事实。

## 2. 范围与非目标

本阶段包含：

- R1：C++ 抽取提示中的状态覆盖指导、对象/主题/时间完整性指导及覆盖诊断。
- B：现有谓词的关系边界、目标完整性和中英文正反例。
- 抽取、准入、Bus、检索共用 C++ 语义和来源校验。
- Python 仅负责 binding、离线重放、人工注释关联和统计。

本阶段不包含：

- 新增同义谓词或临时修改生产 ontology。
- 自动从来源生成候选、按关键词补写候选、答案定向抽取。
- 本地实现阶段不新增真实模型调用；后续小规模调用已由 2026-09-16 设计及用户授权单独覆盖。1031 题全量、时间 QA、生产推广仍不在范围内。
- 修改历史金标、旧回执、旧封存或把离线代理指标写成 F1。

## 3. R1 生成覆盖设计

`claim_extraction_prompt` 继续由 C++ 唯一生成。新增指导必须要求模型逐个检查来源中的明确状态：情绪/感受、明确未决选择、已确定行动、信任关系、明确无所谓等。每个候选须保留同一来源单元中的完整 object、逐字 topic、time_text、actor、scope 和 polarity；没有明确状态时不得为了覆盖率制造候选。

对 Marcus 三类状态，诊断注释分别固定为 `uncertain_about`、`decided_on`、`feels` 的候选期待，记录来源 clause、状态理由和预期对象/时间限定。模型未生成、结构失败、行级拒绝和未执行准入必须保持不同状态。只有完整可审阅响应且人工匹配为空，才允许标记“未生成”。

新增提示指导不得改变输出 schema、候选字段顺序、准入候选数据或默认模式；共享关系目录会同时改变抽取和准入提示，须记录两个提示的哈希。参考例只能使用与 SocialMemoryBench 来源隔离的通用中英文文本，不能出现评测人物、地点、答案或 clause_id。

## 4. B 关系边界设计

继续使用现有五个谓词：`feels`、`trusts`、`decided_on`、`uncertain_about`、`indifferent_to`。先证明现有谓词无法表达后，才允许另行设计新谓词。

- `uncertain_about`：明确尚未解决的选择，包括是否采取一个行动；保留 `POS/BELIEVES`、行动对象和 `yet/仍未` 等限定。单纯可能、不了解世界事实、问题或愿望不算未决选择。
- `decided_on`：明确已经决定或无条件承诺的行动/选择；保留动作否定在 object 中。附带转交、询问负责人等操作安排不自动成为决定，但明确“决定采用某条转交路线”应保留。
- `feels`：情绪或感受及其原因/主题。认知命题、偏好本身不转成情绪；“为偏好某事感到难过”仍可表达情绪。否定关系使用 `NEG` 与 `NEGATED`，对象中的否定内容不重复否定关系。
- `trusts`：对明确人物及任务范围的信任；“相信某责任命题”不等同人际信任。
- `indifferent_to`：对明确主题或选择无所谓；裸 `either way` 必须有可恢复对象。
- `objecting`：若沿用事件通道表达反对，必须保留被反对的目标、主体和来源；缺目标时记录对象不完整，不通过关键词猜测目标。

所有边界先以独立中英文来源测试，再进入提示和准入说明。确定性拒绝只针对候选本身，不能因同话轮其他句子出现偏好、认知或路由词而误伤独立关系。

## 5. C++ 与 Python 职责

C++ 负责提示、参考例、关系目录、结构/来源/语义守卫、候选序列化和诊断字段。新增逻辑必须位于 `src/` 或原生头文件中，并由抽取、准入、Bus、检索共享。

Python 不实现谓词词表、分句、对象匹配、语义拒绝或自动候选生成。Python 只调用原生函数，校验 manifest/receipt 身份，合并显式人工覆盖，输出 `generated/not_generated/unknown/not_executed` 等事实状态。

## 6. 测试矩阵

先写失败测试并保存 RED：

- R1-P01：提示包含状态覆盖、对象/主题/时间完整性指导，且不包含评测人物或答案。
- R1-P02：五类通用中英文来源分别能被原生解析、准入和存储回读；删掉 topic/time 或伪造 topic 必须拒绝。
- R1-P03：重复候选、坏 JSON、超时、空候选分别保持索引和未知状态。
- B-P01：单行动未决、明确决定、情绪与偏好/认知、信任与责任命题、无所谓和反对目标各有正反例。
- B-P02：同话轮存在无关关系词时，合法候选不被整行误拒；关系否定、对象否定和转述归属保持原契约。
- B-P03：完整原文准入、Bus 持久化、检索证据检查与解析共享同一 C++ 规则。

测试不得使用 SocialMemoryBench 人物、地点、问题答案作为提示示例；补充用例不进入历史质量分母。

## 7. 离线评测与停止条件

实现后运行 C++/Python 全套回归、历史 A 140 条流程重放和 S/T 52 条原文重放。R1/B 的变化只与固定原文逐行比较，报告生成数、结构失败、语义拒绝、来源字段完整性和准入执行状态。

若提示或 schema 发生非预期漂移、固定控制出现新增误收、来源/租户校验回退、Python 出现核心逻辑副本，立即停止并回滚该阶段。没有真实模型新回执时，不报告新 F1、QA 或生产质量提升。

生产门槛保持：`semantic_claim_contract=false`、`claim_output_mode=Legacy`、时间视图关闭；本阶段完成不等于可推广。

## R2 谓词覆盖扩展设计同步（2026-09-20）

本阶段承接结构化覆盖诊断和 SourceTurn/三通道回执修复，目标是补齐结构化合同与 legacy mental-state 之间的能力断层。C++ 原生目录版本升级为 `claim-predicate-v3`，新增 `prefers`、`promises`、`doubts`、`believes`、`responsible_for`、`requires`、`forbids` 七类规范谓词及受控别名；既有谓词、来源证据、admission 和持久化格式保持兼容。目录、别名、语义族、允许模态/极性、抽取提示和准入提示均由 C++ `PredicateCatalog` 唯一生成，Python 只绑定、编排和归档，不维护第二份语义逻辑。

本阶段严格执行中文设计文档 → C++/Python RED 测试 → C++ 实现 → 固定协议回归。测试覆盖中英文正反例、错误模态、主体与对象保真、admission 拒绝计数、`knows` 历史模态兼容、三通道证据回读和 Python binding 边界。新增结构化声明数量或离线测试通过率不等于 QA/F1 提升；只有 7/7 scope、36/36 holder 的同协议 SocialMemBench 结果和预注册统计门槛满足后，才讨论晋升。生产默认仍保持 `semantic_claim_contract=false`。

## R2.1 结构化输出协议修正（2026-09-20）

首次 `claim-predicate-v3` 固定评测中，qwen3.8-27b 在 legacy 结构化请求下出现截断、未转义 JSON 和证据范围不完整，57 题中 47 题在抽取建库阶段失败。该结果只说明协议性技术失败，不能解释为谓词扩展导致 QA 下降。下一轮由 C++ `OpenAIAdapter::extract_with_contract` 使用 `ValidationPolicy.claim_output_mode=JsonObject` 发送原生 `response_format`；C++ 继续执行 envelope、schema、scope、admission 和持久化校验，Python 仅传递配置和归档回执，不清洗模型文本。生产默认仍为 `semantic_claim_contract=false`、`claim_output_mode=Legacy`；新评测必须使用独立身份并分别报告技术完成率和 QA。
