## 问题与证据边界

全量基线最终为1031/1031题写入失败、49/49个范围组失败。已持久化的 belief/general_fact 逻辑尝试287次，其中267次为120秒传输超时；没有可用的完整网络记忆和真实回答成绩，因此不把损失直接归给谓词、召回或推理质量。设计初稿在北京时间2026-09-17 00:31曾记录148题/15组终止与87次尝试/78次超时，该进度快照已由上述完整结果取代。

已确认的传播链是：原生 adapter 超时 → Extractor 的旧逻辑最多三次尝试 → 三相提交报告 `extraction_failed` → ladder 停止后续 holder → 当前范围所有题无法进入 QA。普通失败不会必然回滚另一通道的成功声明；episodic 失败当前按无事件处理。

部分成功的 general_fact 返回 `[]`，却报告上千 completion token。账本没有完整响应，故思考耗时、正文长度、输入规模和服务波动都仍是假设。当前代码只发送 temperature 和 max_tokens 等通用字段，没有显式 `enable_thinking`；这既不能证明该模型默认启用思考，也不能证明 max_tokens 限制了全部思考 token。已归档 DashScope SDK 文档支持通用思考参数，但没有 qwen3.8-27b 特定默认值的证据。

## 选择与顺序

先在基线结束后恢复请求边界的可观测性，用冻结原生 adapter 直接执行最少量的固定开发样本，保存现有 `LLMResponse.to_json()`。此阶段不改提示、不改生成设置、不改解析，也不重发基线中失败的题目并回填得分。诊断结果只解释调用行为。

根据回执选择下一项单变量实验：若思考相关字段和耗时支持该假设，在 C++ 增加显式可选思考开关后对比默认与关闭；若主要是正文截断或输入过长，则另行设计输出/输入预算方案。单纯延长超时会增加成本和等待，不能先假定它能修复根因。取消整组失败虽可能恢复部分回答，但会同时改变失败语义，放在独立后续轮次，不能用它掩盖抽取失败。

进入第二步的预定判据是：第一步任一原始响应具有非空 `reasoning_content`、正数 `completion_tokens_details.reasoning_tokens`，或原始正文开头有完整 `<think>…</think>` 段；也允许在至少一次请求触发 timeout 或 `finish_reason=length` 时进入**未确认原因的单变量假设检验**。后两者只证明预算下不可用，绝不等同于确认思考耗时是根因。两次响应均完整且无上述证据则停止本专项，回到写入/表示损失分析。鉴权、模型不存在或请求协议被拒绝则停止依赖请求并记录技术阻断。

本轮首先处理模型调用能否完成；谓词丰富度、来源连续写入、归属、时间和跨 holder 召回继续按总体设计处理，待具有实际可检索记忆后用逐题证据选择优先级。

## 固定诊断输入与预算

只用 `network-split.json` 中的开发网络。输入由冻结公开历史构成，使用与基线相同的 speaker 分组、holder 排序、提示构造和来源范围；不读取参考答案或保留集逐题内容。请求清单必须在首次请求前保存来源哈希、模型、提示哈希和配置。不得依据一次成功或失败临时换样本。

第一步最多 2 次请求：固定一个开发范围的首个 holder，分别执行 belief 与 general_fact 的首次原生请求。使用 qwen3.8-27b、120000 ms、4096 max_tokens、零传输重试；不执行原生 Extractor 的三次逻辑重试，不写入记忆，不做 QA 或裁判。完整 HTTP 回执若仍不足以分辨原因，如实保留未知。

条件满足后，第二步最多 8 次原生请求：两个固定开发范围，两个通道，每条同一提示分别采用默认与显式关闭思考两种设置。选择按输入长度覆盖短、长两个范围；交错执行两种设置，避免顺序与服务时段完全重合。模型、来源、提示、timeout 和 max_tokens 不变，成功/失败都保留，不进行按结果补跑。这是有界诊断，不替代完整复测，也不把一次恢复宣称为稳定因果关系。

诊断最多 10 次原生请求，独立计账，不使用旧实验剩余预算，不与正在运行的 baseline 竞争并发。结果不足则保留未确定结论，另写下一轮有界实验，不自动反复请求。

第一步固定按较短输入的 belief、general_fact 顺序执行两次默认设置请求，单次120秒、零重试。第二步不得复用第一步的默认响应；它们属于不同时段的独立请求。第二步的四对调用顺序预先固定如下：

| 第二步序号 | 输入 | 通道 | 设置 |
|---|---|---|---|
| 1 | 较短 | belief | 未设置思考开关 |
| 2 | 较短 | belief | 显式 false |
| 3 | 较短 | general_fact | 显式 false |
| 4 | 较短 | general_fact | 未设置思考开关 |
| 5 | 较长 | belief | 显式 false |
| 6 | 较长 | belief | 未设置思考开关 |
| 7 | 较长 | general_fact | 未设置思考开关 |
| 8 | 较长 | general_fact | 显式 false |

每条请求发送前先持久化唯一预约和开始标记；重复或崩溃后未知状态禁止自动重发。结果以请求序号单独保存完整原生回执、所用核心/提示/配置哈希与耗时。第一步最多2、第二步最多8、总计最多10；超时和失败均消耗一次额度，不补发。普通超时和5xx保留在对应臂的固定分母中继续；401/403/404或400请求拒绝停止余下调用，将它们标为未执行，不能冒称完整四对实验。没有完整响应时 usage 保持未知。

第一步清单绑定当前冻结核心；第二步必须在 C++ 开关完成测试后再冻结独立核心，并从新核心的本机实际请求捕获两臂请求体哈希。默认臂必须与现有捕获字节的 JSON 内容一致，false 臂只能多出布尔 `enable_thinking=false`。Python 只选择配置与提示、调用原生 adapter、预约及保存回执，不直接修改请求体发送。核心和逐臂请求身份未核验时不能启动第二步。

第二步一次性编排脚本与测试保存在独立诊断目录。先用离线失败用例覆盖：预约先于发送、已有终态不重发、开始后无回执不重发、400停止且余项未执行、超时继续并保持固定分母；再实现调度。进程级文件锁防止并发重复预约，预约与回执使用原子替换并刷新落盘。真实执行入口还须逐字段将八条记录与原冻结计划比对，只接受default/off；核验封存基线终态文件的哈希以及1031题/49组均完成；把原始请求、捕获wire、相同核心和相同配置绑定后，才允许预约发送。真实执行前核验冻结文件、请求体、提示和脚本哈希；脚本只调用原生 adapter，不复制 HTTP 或抽取语义。同核心本机捕获仅证明本机构造的wire，不能说已获取DashScope服务端收包哈希。该测试是计账/恢复行为证据，不能算模型质量证据。

## 条件性 C++ 改动与测试要求

只有满足上述预定第二步判据后才实施显式开关：`OpenAIAdapter::Config` 增加可选布尔 `enable_thinking`，默认未设置。C++ 统一构造所有普通、结构化和流式请求的可选字段；未设置时不发送字段，显式 false 必须发送 JSON 布尔 false。binding 只映射此配置，不拼装请求、不复制语义逻辑。不能根据模型名猜测默认值或在供应方拒绝时静默去掉参数重试。

先写独立失败测试，再实现。测试必须捕获原生 libcurl 实际发出的本地 HTTP 请求，覆盖默认缺省、显式 true/false、流式一致性、结构化调用一致性，以及服务端拒绝时不静默回退。binding 仅验证可选值的往返与原生行为调用。既有 schema 校验和正文处理不因开关变更而放松。

抽取三通道完整回执的长期接口另作可观测性改动：C++ 持有并序列化原始响应，Python 只落盘与计数。当前两步诊断直接使用原生 adapter 已存在的完整回执，避免为一次根因探查重构整个写入接口。不会宣称此次基线已具有不可恢复的旧回执。

## 验收与归因

本专项只报告完整 HTTP/envelope 响应比例、可见正文是否为空、finish_reason、可见 usage、未知用量次数和延迟；有 reasoning token 细项才报告细分，没有则保持未知。直接 adapter 回执不执行 `parse_extractor_json`，因此本专项的原生抽取解析、候选数和实际入库接受数均标为未测，不能把 Python JSON 解码计数冒充原生结果。有效 `[]` 可是解析成功且零候选，不能因无声明而自动判为协议失败。完整写入复测再使用现有 C++ 解析和提交统计。原始回执只归档必要响应，不记录密钥或 Authorization。

四对实验只用于选择局部可用性候选；即使显式 false 恢复全部四次响应，也不足以排除服务时段波动或证明总体因果效应。第一步的两次响应另列，不能混入第二步配对分母。
